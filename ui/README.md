# PHASE 3 — Inspection UI

**Not built yet, deliberately.** The data contract it depends on already exists,
so this can be built at any time without touching the rest of the system:

- `schemas/trace_event.schema.json` — the full event schema
- `examples/runs/run_*/` — a real trace generated by `trance bundle`, committed
  so the UI can be developed against actual data rather than mocks

## What it needs to show

1. **Timeline / tree of a run.** `parent_event_id` gives you the tree directly:
   a `curate` event parents the `agent` event that consumed its bundle, which
   parents each `tool_call` the worker made.
2. **The context payload per run.** `context_bundle.rendered` is the verbatim
   prompt text; `context_bundle.items[]` is the same thing structured, with
   `hops` and `include: body|signature` per symbol. Syntax-highlight it and
   group by file.
3. **Graph slice against the full repo graph.** `graph_slice.nodes/edges` is the
   subset the curator walked. Render the full graph from SQLite dimmed, the
   slice highlighted — that picture *is* the pitch for the whole project. Color
   edges by `resolution` (green = lsp/same_file, yellow = ambiguous, red =
   unresolved) so gaps in static analysis are visible.
4. **Token in/out.** `context_bundle.stats.est_tokens` vs `stats.baseline_tokens`
   (what whole-file context would have cost) is the savings number. `usage` on
   `agent` events carries real API counts once PHASE 2 lands; `usage.estimated`
   tells you which is which — never plot the two without distinguishing them.

## Suggested build

Plain Vite + React + TypeScript, reading the trace files over a tiny static
server (`python -m http.server` over `examples/` is enough to start). No backend
needed: a run is a directory of JSON. Add `trance serve` later only if live
tailing of an in-progress run turns out to matter.

For the graph view, `d3-force` or `elkjs`. Avoid a heavy graph library until the
node count justifies it — a curated slice is 10–50 nodes.
